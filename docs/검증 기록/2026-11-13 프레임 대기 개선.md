# 프레임 대기 개선 검증 기록

## 원인과 변경 범위

물리 예제의 수정 전 실측은 Python 갱신 30.24FPS, WebSocket 장면 전달 30.31FPS였다. 입력 조회·물리 요청·장면 전송을 순차로 기다리며, 각 요청이 세션 소유 스레드의 주기적인 대기를 거쳤다. 이 환경에서 Thread.Sleep(5)의 평균은 9.63ms, 네트워크를 제외한 세 번의 직렬 요청 대기는 28.99ms였다. 두 객체의 실제 물리 계산 평균 0.022ms보다 요청 대기가 프레임 시간을 지배하였다.

C#은 요청이 들어오면 소유 스레드를 즉시 깨우고, 요청이 없으면 다음 게시·브라우저 종료 시각까지 기다린다. 단일 소유자와 요청 순서, 제한된 큐와 묶음 처리 방식은 유지한다. Python에서 도착한 새 장면은 소유 스레드의 요청 묶음을 처리한 뒤 즉시 게시하며, 출력·상태만 바뀐 알림은 주기적으로 합친다.

Python은 고해상도 단조 시계에 고정한 다음 프레임 목표 시각을 유지한다. 짧은 대기 지연은 다음 대기에서 보정하고, 긴 지연으로 놓친 프레임을 연속 재생하지 않는다. 이동·타이머에는 실제 경과 시간을 보존한다. 양수 시간의 프레임 대기는 별도 작업에서 수행하여 이벤트 루프를 막지 않는다. 물리 계산의 1/120초 고정 간격은 유지한다.

구현 변경은 RuntimeSession, BrowserLifetime과 Python 실행기의 프레임 대기에 한정한다. 요청·종료·장면 게시와 가상 시계 회귀 테스트, 재현용 성능 측정 스크립트 및 관련 문서를 함께 보완하였다. 학생 예제의 원본과 브라우저 화면 코드는 변경하지 않았다.

## 환경과 산출물

2026-11-13 KST의 Windows x64 개발 컴퓨터에서 .NET SDK 10.0.404, Python 3.13.18, Node.js 24.15.0, PowerShell 7.6.9, Pyright 1.1.414를 사용하였다.

폴더 배포본은 artifacts/fps-validation이다. 새 임시 폴더로 빌드한 최종 wheel은 artifacts/wheels/blackpy-0.1.1-py3-none-win_amd64.whl이며 크기는 48,960,947바이트이다. SHA-256은 `4a730076d83e6bed7d2d3eef77929f83f598ad532b34ade684abfa22ff6ad386`이다. Twine strict 검사를 통과하였다.

## 성능 실측

다른 빌드·테스트를 중단한 상태에서 다음 명령으로 측정하였다.

```powershell
$env:BLACKPY_DISTRIBUTION = Join-Path (Get-Location) 'artifacts/fps-validation'
node scripts/Measure-FrameRate.mjs 20
```

06-physics의 임시 복사본에서 점프와 초기 위치 복귀를 반복하였다. 처음 3초를 제외하고 WebSocket은 약 20초, Python 기록은 마지막 저장 시점까지 약 18.97초를 수집하였다. 두 평균 갱신률 모두 목표 범위인 58.5~61.5Hz를 충족하였다.

| 측정 | Python 갱신 | WebSocket 장면 전달 |
| --- | --- | --- |
| 평균 | 60.002FPS | 60.262FPS |
| 평균 간격 | 16.666ms | 16.594ms |
| 중앙값 간격 | 16.658ms | 16.651ms |
| 95백분위 간격 | 17.670ms | 17.645ms |
| 최대 간격 | 25.073ms | 25.145ms |
| 33.333ms 초과 | 0/1138 | 0/1204 |

WebSocket 수치에는 출력·상태 변경에 따른 장면 포함 알림도 들어간다. 실제 브라우저 canvas의 화면 표시 FPS를 직접 계측한 수치는 아니다. 런타임 갱신·장면 전달과 화면 표시의 검증 경계를 구분한다.

입력 조회·물리 요청·장면 전송의 평균 왕복 시간은 각각 0.375ms·0.392ms·0.362ms였다. 소유 스레드의 세 번 직렬 요청은 별도 진단에서 28.989ms에서 0.043ms로 줄었다.

첫 개선에서는 평균 약 60Hz에 도달했으나 Python의 Windows 이벤트 대기와 C#의 별도 게시 시계 때문에 95백분위 간격이 약 30ms였다. Python 대기를 이벤트 루프 밖으로 옮기고 새 장면의 추가 게시 대기를 제거한 뒤 위의 최종 결과를 얻었다. 평균 처리율과 개별 프레임 간격을 함께 확인하였다.

최종 원자료는 [프레임 측정 결과](../../artifacts/test-results/frame-rate-1794500031668/report.json)이다. 초기 원인 진단과 요청 대기 비교는 artifacts/diagnostics의 physics-frame-1794499096520 및 physics-latency-20261113에 있다.

## 회귀 검증

[Testing](../Testing.md)의 전체 자동화 검증을 수행하였다. .NET 테스트·폴더 배포·wheel 빌드는 순차로 실행하고, 실제 FPS 측정은 다른 검증과 동시에 실행하지 않았다.

| 검증 | 결과 |
| --- | --- |
| 의존성 | 로컬 NuGet 패키지 2개의 해시·직접 참조 확인 통과이다. |
| C# | 107/107 통과이며 빌드 경고·오류는 없다. |
| Python | 79/79 통과이다. |
| 통합·이벤트·물리·텍스트 입력·브라우저 수명·샘플 | 37/37 통과이다. |
| 웹 | 33/33 통과이다. |
| 설치형·편집기·샘플 진입점·직접 실행 | 최종 wheel에서 29/29 통과이다. |
| 배포 | 동봉 런타임·라이선스·학생 파일 보존·한글 경로·종료 등 별도 10개 항목 통과이다. |

테스트 러너 합계는 285/285이다. 새 검사는 유휴 상태의 요청·종료, 큐 한도를 넘는 요청 묶음, 요청이 없는 동안의 브라우저 종료 기한, 512개 장면 요청의 최신 상태 게시와 재시작, 가상 시계의 짧은 지연 누적 방지 및 200ms 지연 후 실제 시간 보존을 포함한다.

주요 출력은 artifacts/test-results의 fps-measurement.log, fps-integration.log, fps-wheel.log, fps-installed.log, fps-deployment.log에 있다. 수정한 코드·설정·문서 9개 파일의 UTF-8 무BOM·LF·마지막 개행을 확인하였다. 전체 diff 공백 검사에는 기존 samples/02-keyboard/고양이.py의 마지막 빈 행 한 건이 남아 있으며 해당 기존 변경은 수정하지 않았다.

## 확인 범위

성능 수치는 위 Windows·Python 환경과 두 객체 물리 예제의 결과이다. Python 3.10의 타이머 정밀도, 다른 장비·브라우저의 실제 화면 표시 FPS, SDK가 없는 별도 PC와 실제 VS Code 버튼 조작은 이번 검증에 포함하지 않았다. 기능 테스트의 가상 30·60·120FPS 검사를 실제 처리율의 증거로 대신 사용하지 않았다.

검증용 복사본과 임시 가상환경을 사용하였으며 기본 Python 환경의 패키지를 교체하지 않았다. 커밋·푸시·GitHub Actions 실행·PyPI 공개는 수행하지 않았다.

검증용 실행부와 관련 Python 프로세스의 종료를 확인한 뒤, artifacts/fps-validation의 실행부로 원본 06-physics 예제를 브라우저에 다시 열었다. 실행 상태가 running임을 확인하였으며 사용자의 직접 확인을 위해 실행해 둔 상태이다.
